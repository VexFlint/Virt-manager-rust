# Rust conversion of virt-manager

## Destination

A locked, hand-off-ready build spec for a full Rust rewrite of virt-manager
(GUI + `virtinst` core + `virt-install`/`virt-clone`/`virt-xml` CLI tools),
targeting Linux only, matching the existing GTK UI's screen layout and
behavior closely, with full driver parity across whatever libvirt backends
`virtinst`/domcapabilities expose (QEMU/KVM, Xen, LXC, bhyve, etc.) — not the
working code itself, which gets handed to `/to-spec`/`/to-tickets` once the
map's tickets are resolved.

## Notes

- Domain: virtualization management (libvirt/QEMU-KVM), desktop GUI + CLI tools.
- Upstream reference: virt-manager 5.1.0, installed source at
  `/usr/share/virt-manager` on this machine (`virtManager/` 28.9k LOC GUI,

  https://github.com/virt-manager/virt-manager (pull `tests/` from there —

## Decisions so far

- [Destination](./map.md) — locked build-spec, Linux-only, close GTK UI
  match, full libvirt driver parity. (See Destination section above; this is
  the map's own founding decision, not a separate ticket.)
- [GTK4 console-widget availability](./issues/01-gtk4-console-widget-availability.md) — no: neither `gtk-vnc` nor `spice-gtk` has a GTK4 build, on any mainstream distro. A `gtk4-rs` UI gets no free console widget either — kills the main premise for choosing it over `egui` on that basis. Ticket 05 is now unblocked.
- [virt crate API coverage](./issues/02-virt-crate-api-coverage.md) — full coverage of migration/snapshots/nodedev/secrets/storage/capabilities; the one gap is domain/network/nodedev/secret/storage-pool event registration. **Amended by ticket 09**: upstream actually solves this via `libvirt-glib` (gir-bound, no GTK in the link chain), not a hand-rolled shim — bind it instead, for however much of the gap its `domain-added`/`domain-removed`/`started`/`stopped` signals cover.
- [Upstream test suite inventory](./issues/03-upstream-test-suite-inventory.md) — ~316 golden-XML fixtures (254 CLI compare + 62 xmlparse round-trip) spanning QEMU/KVM/Xen/LXC/Virtuozzo/bhyve/HVF and a wide OS/device matrix; this is the acceptance-bar corpus for the Rust port. Ticket 06 is now unblocked.
- [libosinfo bindgen feasibility](./issues/04-libosinfo-bindgen-feasibility.md) — practical: pure GObject C API, no GTK in the link chain, tiny init sequence, osinfo-db is a separately-versioned distro-installed data package with its own update tooling. Feeds the OS-detection/create-VM-wizard fog once tickets 05/06 land. **Reasserted 2026-08-23** after tickets 09/14/15 drifted into calling it "gir-bound" by unchecked analogy: tested both real generators against this machine's actual libosinfo — `gir`'s idiomatic-wrapper mode stubs out the functions that matter most here (the whole init sequence, every `*_list()`/`guess_os_from_*`/`identify_*` function, ~60 of ~95 tested) since its heuristics don't handle libosinfo's `(void, GError**)` functions or custom list container types; plain `bindgen` gets all 463 functions unstubbed with no `Gir.toml` config-authoring detour. `bindgen` stands as originally concluded — the three drifted tickets and `osinfo/mod.rs` corrected to point back here. **Built**: `build.rs`'s `bindgen` pass (allowlist `osinfo_.*`/`Osinfo.*`, blocklist the entire transitively-pulled-in glib/gobject/gio type universe and re-point it at `glib-sys`/`gobject-sys`/`gio-sys`'s own real types via `raw_line`s) plus a minimal hand-written safe wrapper (`osinfo::{OsDb, OsInfo}`, matching ticket 15's planned shape) running libosinfo's real init sequence and verified against this machine's actual installed `osinfo-db` (a permanently-archived Fedora 25 entry, chosen to stay stable as the package grows). **A real mistake caught on review**: a first draft inferred GObject transfer-ownership from C function names rather than checking it, and got one of four calls backwards (`osinfo_db_get_os_list` is `transfer-ownership="full"` despite its `get_` prefix) — a use-after-free too subtle for a short test process to reproduce, caught by reading the actual `.gir` file's transfer annotations directly instead of trusting the naming convention. 184/184 `virtinst-core` (+3), harness 61/61, `fmt`/`clippy` clean; not yet run under a memory sanitizer (no `valgrind`/nightly toolchain in this environment), flagged rather than silently skipped.
- [GUI toolkit choice](./issues/05-gui-toolkit-choice.md) — `gtk4-rs`: neither toolkit gets a free console widget (ticket 01), which cancels out both the "free widget" case for `gtk4-rs` and the "avoid GtkVnc/SpiceClientGtk binding risk" case for `egui`; on the remaining ~95% of the app, `gtk4-rs` gets close-GTK-match fidelity (theming, HIG, AT-SPI) by construction. Console rendering originally planned pure-Rust-first; **amended by ticket 14** — in practice both channels ended up gir-bound.
- [XML modeling approach](./issues/06-xml-modeling-approach.md) — typed structs bound to XPaths via a derive macro, reading/writing through a mutable order-preserving DOM built on the `edit-xml` crate. Neither original option alone satisfies ticket 03's acceptance bar (byte-exact round-trip of untouched XML, `virt-xml --edit` preserving foreign `xmlns:qemu` elements) without converging here anyway — this gets Rust compile-time field safety plus upstream's preserve-the-rest-of-the-document behavior, without porting xmlbuilder.py's runtime dynamic-dispatch descriptor engine.
- [GUI screen inventory](./issues/07-gui-screen-inventory.md) — the map's 15-screen list is really 17 top-level screens (`docs/research/gui-screen-inventory.md` has the full `.ui`-to-controller table) plus a 13-item shared sub-widget layer the original list missed. Inventory only, no per-screen specs yet — those are separate tickets, opened as needed.
- [Create VM wizard](./issues/08-create-vm-wizard.md) — `GtkStack` state machine, hand-written transition/skip `match` functions (one real skip rule), incrementally-mutated `WizardState` (plain struct, `Option<T>` fields, no typestate), `InstallMethod` enum-of-structs for compile-time-exhaustive per-method fields, `Guest` built directly at Finish bypassing ticket 06's DOM layer (nothing to preserve on a fresh document). Spun off the async-detect-gate question as ticket 09 and deferred the "customize before install" handoff to the not-yet-opened VM-details-window ticket. **Amended by `virt-install --import` (ticket 16, 2026-08-20)**: "direct struct construction, fresh serialization" doesn't mean `Guest::to_xml_string()` — that only serializes flat fields, since `devices`/`vcpulist`/etc. are read-only-by-design `#[xml(nested)]`/`#[xml(list)]` (ticket 06's own preservation guarantee requires it). Fresh creation has to go through direct `edit_xml::Document`/`Element` construction instead, same primitives ticket 16's `cloner.rs` already uses for DOM surgery — applies to the real wizard too, not just the CLI. See the ticket file's amendment note for the full reasoning.
- [Async / background-task model](./issues/09-async-background-task-model.md) — two separate problems: libvirt's own event loop binds `libvirt-glib` via `gir` (what upstream actually does, found in `virtmanager.py`'s bootstrap — amends ticket 02); blocking-call offload is plain OS threads + `glib::MainContext::channel()`, no `tokio` (every `virt` call is synchronous, nothing for a runtime to multiplex). Cooperative `Arc<AtomicBool>` cancellation, one shared progress-modal wrapper all long-running calls route through, matching upstream's `asyncjob.py` exactly.
- [VM details window](./issues/10-vm-details-window.md) — `GtkListBox` for the `hw-list` sidebar (a dozen-ish rows, not `ListView`-scale), direct port of upstream's pending-edit/Apply architecture (edits scoped to the selected row, confirm-or-discard on switch), a per-`HW_LIST_TYPE` `Option<T>`-field pending-edit struct (not an enum-of-structs — row fields can be simultaneously dirty, unlike ticket 08's mutually-exclusive `InstallMethod`). Remove Device is immediate, routes through ticket 09's async wrapper. Spun off Snapshot management as ticket 11 and deferred the live/persistent (`AFFECT_LIVE`/`AFFECT_CONFIG`) config duality to the `virtinst-core` ticket. **Amended by ticket 12** with that duality's concrete shape.
- [Add Hardware wizard](./issues/12-add-hardware-wizard.md) — `enum NewDevice` (17 mutually-exclusive variants, same compile-time-exhaustive pattern as ticket 08's `InstallMethod`), companion-controller dependencies folded directly into a variant rather than a bolted-on side-channel. Found and ported the concrete live+persistent attach pattern (`attach_device()` then always `add_device()`, degrading to persistent-only on hotplug failure) — the answer ticket 10 had deferred. Device-default dispatch stays opaque, deferred to the not-yet-opened per-driver-defaults item.
- [Snapshot management](./issues/11-snapshot-management.md) — resolved by verified precedent, not a fresh grilling round (see ticket file for the source checks this rested on, including a first-read widget guess that source-reading corrected before it got written down). `GtkListBox`-with-custom-row-widget for the snapshot list (one rendered column, not the six-column tabular grid it first looked like; confirmed no parent/child snapshot tree is displayed), create/revert/delete already on ticket 09's `vmmAsyncJob` rails, `enum NewSnapshot` for the mutually-exclusive internal/external/disk-only creation modes, snapshot-XML construction opaque-deferred to `virtinst-core` same as ticket 12's device defaults.
- [VM Manager main window](./issues/13-vm-manager-main-window.md) — row-activation dispatch, live-stats feed, and delete/context-menu actions settled by precedent (tickets 09/10). The one real fork — this is the app's only genuine two-level tree (connections → VMs), not a flat list like tickets 10/11, and `gtk4-rs` still ships (deprecated-since-4.10 but present, verified against the actual GTK4 typelib) `TreeView`/`TreeStore`/`CellRenderer*` — decided **`GtkListView` + `GtkTreeListModel` + `GtkTreeExpander`** over the deprecated 1:1 port; the custom `CellRendererSparkline` becomes a small `GtkWidget` subclass drawing via `snapshot()`, bound per-row through a `GtkListItemFactory`.
- [Console-viewer implementation specifics](./issues/14-console-viewer-specifics.md) — SSH tunneling is just shelling out to the system `ssh` binary (`os.fork`+`os.execlp`, verified in `sshtunnels.py`), no crate needed. Checked the actual crates rather than trusting ticket 05's names: `spice-client`'s audio/clipboard/USB-redirect are unimplemented and upstream genuinely uses all three, so SPICE escalates to gir-bound `libspice-client-glib` immediately. VNC likewise: `vnc-rs` is `tokio`-based (conflicts with ticket 09's no-async-runtime decision), `whitequark/rust-vnc`'s own README admits no auth/encryption at all — decided to skip pure-Rust VNC entirely and bind `libgvnc` via `gir` too. **Amends ticket 05**: both console channels end up gir-bound, not pure-Rust-first as originally planned.
- [virtinst-core module/crate boundaries](./issues/15-virtinst-core-crate-boundaries.md) — one crate, not several (no proven need yet to pay workspace/versioning overhead for a split), internal modules mirroring upstream's own `virtinst/` package layout almost 1:1: `devices`/`domain` (typed structs per tickets 06/08/12), `connection` (wraps `virt` + `libvirt-glib` per 02/09, also where ticket 12's attach+persist pattern and ticket 10's deferred live/persistent duality land), `osinfo` (wraps `libosinfo` per 04), `install` (backs ticket 08's `InstallMethod` variants), `capabilities` (feeds per-driver defaults), `cloner` (added per ticket 16). `xmlbuilder.py`/`xmlapi.py` explicitly not ported — ticket 06 already rejected that engine. The shared async-job wrapper (09) stays GUI-shell, not core — it shows a modal, `virtinst-core` has no GTK dependency.
- [CLI tools](./issues/16-cli-tools.md) — `virt-install`/`virt-clone`/`virt-xml` share `virtinst-core` entirely with the GUI (confirms ticket 15's one-crate call), thin CLI-specific shell on top (stdout progress, `y/n` prompts). Upstream's `--disk path=/foo,bus=virtio` option-string syntax isn't the dynamic engine ticket 06 rejected — it's a declarative cliname→propname mapping, so it's preserved exactly via a derive-macro extension rather than redesigned. `virt-xml --edit` is the first real end-to-end validation of ticket 06's order-preserving DOM (the exact scenario it was built for) and it holds — "cold start, one edit, done" is the *simpler* case relative to ticket 10's in-process multi-edit session, which was already designed for. `virt-install` reuses ticket 08's `InstallMethod` as-is: `--unattended`/`--cloud-init` thread through as extra fields on relevant variants (found by checking the actual argument groups — they're modifiers, not separate methods), `--reinstall` is its own CLI-only operation closer in shape to `--edit` than to the wizard.
- [Per-driver device-default behavior](./issues/17-per-driver-device-defaults.md) — much more contained than it sounds: grepped the whole `devices`/`domain` tree and only 9 files branch on driver family at all, each an ordered per-*field* decision chain (driver family + guest OS/machine + live capability query), not a pervasive axis. No driver-strategy trait — a trait-per-driver would need one method per field anyway, more ceremony than upstream's already-reasonable structure. Direct port of the ordered-chain shape, typed instead of duck-typed. `DomainCapabilities` gets its own lightweight deserialize-only path, separate from ticket 06's DOM — it's read-only and cached, none of the order-preservation machinery does anything useful there.
- [Packaging/release process](./issues/18-packaging-release-process.md) — GPLv2-or-later (matching upstream; the repo had no `LICENSE` file at all, a hard blocker — now fixed, standard FSF GPL-2 text copied in). Distribution: traditional `.deb`/`.rpm` packages only for now, Flatpak deliberately not pursued — its sandbox model is in real tension with what this app needs (`qemu:///system`, SSH keys, raw device access) and nothing's shown that's worth solving before the port exists. CI/build: x86_64 Linux only for v1, matching the already-locked Linux-only scope. Deliberately not decided: release cadence, actual CI pipeline contents, packaging metadata — none of that is designable before there's a `Cargo.toml` and working code.

- [CLI golden-corpus comparison harness](./issues/19-cli-golden-corpus-harness.md) — upstream's own `tests/test_cli.py` corpus (ticket 03's acceptance bar) isn't uniformly reachable against a real libvirt driver: the majority of it (`URI-KVM-X86` alone is 36 of ~82 URI references) depends on a Python-level `libvirt.open()` interception (`MagicURI`) that injects fake capabilities/domcaps XML, which the real `virt` crate has no equivalent seam for. Starting against the `URI-TEST-FULL`/`URI-TEST-REMOTE` subset (real `test:///`, no injection needed) to get a harness and baseline running now; a `virtinst-core` capability-override layer for the KVM/x86 subset (36 more fixtures, highest-leverage slice) is scoped as necessary follow-up work, not a blocker. Harness later grew to 11 `virt-xml` devices and a field-match `--edit`/`--remove-device` selector form (61 checks / 26 cases) before this capability layer was scoped in ticket 20.
- [Capability-injection layer for virt-install's fake-arch corpus](./issues/20-capability-injection-layer.md) — full `MagicURI` trace (not just ticket 19's summary): it fakes `getCapabilities`/`getDomainCapabilities` *and* separately fakes the reported connection URI (`fakeuri`) so `is_qemu()`-style scheme checks pass while the real call still hits the harmless `test://` driver — a real safety consideration on this machine specifically, which has a working real QEMU/KVM x86_64 driver that a naive `--connect qemu:///system` fake would actually hit. 66 fixtures total gated behind this (counted exactly, not estimated), across 8 fake-arch URIs. Two exploitable seams already exist (`DomainCapabilities::fetch`/`::parse`'s existing split; `Connection::uri()`'s already-client-side URI parsing) but host `Capabilities`/`guest_lookup` doesn't exist in Rust at all yet — a real gap ticket 17 didn't flag. Split into two separate future decisions rather than one ticket: (a) build the injection layer, (b) actually complete virt-install's own defaulting to reach fixtures with it. **(a) is now built**: `capabilities::caps` (host `Capabilities`/`guest_lookup`, ported in full including its exact error messages), env-var gates on both `fetch` functions (`VIRTINST_TEST_CAPS_FILE`/`VIRTINST_TEST_DOMCAPS_FILE`), and `Connection::open`'s `VIRTINST_TEST_FAKE_URI`. Found and fixed a real test race along the way (two pre-existing tests failed intermittently under parallel `cargo test` once these env vars existed at all) by broadening the crate's existing `TEST_DOMAIN_LOCK` rather than adding parallel single-purpose locks — every test calling `Connection::open`/either `fetch` now holds one shared lock. **(b) started, minimal slice**: `virt-install.rs` now calls `Capabilities::fetch` + real `guest_lookup(None,None,None,None)` instead of `DomainCapabilities::fetch(None×4)` for `hypervisor_type`/`arch`, and threads the newly-available `os_type` through all five non-container document builders (`--container` deliberately excepted — it hardcodes `"exe"` for a real, traced reason, see the ticket). `DomainCapabilities::fetch` no longer called anywhere in `virt-install.rs` (no remaining consumer there). Every existing install-module end-to-end test passed unchanged, confirming the swap is behavior-preserving. `loader`/`emulator`/`machine`/CPU/clock/PM/9-file matrix remain entirely unstarted — the larger remainder of (b), now itself scoped in [ticket 21](./issues/21-set-defaults-scope.md).
- [Scope of guest.py's set_defaults](./issues/21-set-defaults-scope.md) — ticket 20's one-line label for piece (b)'s remainder undersold it by roughly an order of magnitude: `set_defaults()` is `_set_default_machine`/`_set_default_uefi`/nine `_add_default_*` device pushers/per-device `set_defaults` (the 9-file matrix)/`clock`/`cpu`/`features`/`pm`/`os`/spice, not three things. Traced the reachable subset (this crate's only real driver/arch combos: i686/x86_64 on `test:///`/`qemu:///system`) line by line. The real constraint is `OsInfo` (blocked on the `gir` tool): UEFI/loader selection and the disk-bus virtio-vs-ide real default are **fully blocked** on it for every reachable path — not worth picking up piecemeal. Six things are buildable now with zero `OsInfo` dependency, found by tracing rather than assuming: `emulator` threading, `machine`'s fallback-only branch (`capsinfo.machines[0]`, the q35-preferred branch stays blocked on `OsInfo` **and** an unbuilt hv-version support-check mechanism), `graphics`'s spice/vnc default type (needs one new `DomainCapabilities` query method on data already parsed), `clock`'s rtc/pit/hpet timer trio for x86+qemu, `hostdev.set_defaults` (currently unreachable from any CLI flag), and — the real surprise this pass — CPU mode defaulting (host-passthrough/host-model/host-model-only), which is *not* `OsInfo`-blocked at all but needs `domcaps.rs`'s `<cpu>` section built first (ticket 17's own "not yet built" list). Nine `_add_default_*` device pushers/`pm`/`os`/`features`/spice not individually traced this pass, flagged rather than assumed covered. Scoped, then user picked slices (a)+(b) via `AskUserQuestion`: **built** — `build_domain_skeleton` and all five non-container document builders gained `machine`/`emulator` params (`build_container_os_document` deliberately excluded, same reasoning as its `os_type` exception), `virt-install.rs` threads both from the same `capsinfo` ticket 20 already resolves, verified against the real `test:///default` driver (not just this crate's own serialization) that a defined domain keeps a real `<emulator>` element. Slices (c)–(f) — `graphics` default type, `clock`'s timer trio, `hostdev.set_defaults`, CPU mode defaulting — remain unbuilt at that point. **A real, unrelated bug found and fixed while continuing this ticket**: every builder derived the default NIC's OUI from `domain_type == "qemu"` (a literal string match on `hypervisor_type`) instead of the connection's real URI scheme (`Uri::is_qemu()`, what `cloner.rs` already correctly uses) — since a real KVM-accelerated `qemu:///system` resolves `hypervisor_type` to `"kvm"`, not `"qemu"` (confirmed against this machine's own real capture), every real, non-`test:///` domain this crate has ever built got the Xen OUI instead of qemu's. Not a ticket-21 regression — a pre-existing bug since `virt-install.rs`'s first version, invisible in this crate's own `test:///`-only test suite. Fixed by threading a real `is_qemu: bool` through every builder (including `--container`, which — unlike `os_type`/`machine`/`emulator` — has no "wrong guest" hazard since `is_qemu` isn't `capsinfo`-derived). Initial regression test passed `is_qemu` as a literal, which proved the callee but not the derivation; closed on review with a composition test that injects `hypervisor_type=kvm` and a fake `qemu:///system` URI together and asserts on `conn.uri().is_qemu()` itself, manually confirmed to fail against the old derivation. **Refactor before (c)**: collapsed the 6-field `domain_type`/`os_type`/`arch`/`machine`/`emulator`/`is_qemu` cluster (each threaded on separately across the work above) into one `GuestCapsDefaults` struct, reused by all five non-container builders — pure refactor, zero test-assertion changes, verified as such. **(c) built**: `domcaps.rs` gained `supports_graphics_spice`/`default_graphics_type` (its first `supports_*`-style query methods, taking `uri: &Uri` rather than separate `bool`s after a review caught the transposition risk of the latter and confirmed `Uri::parse` is connection-free) and `domain_skeleton::push_default_graphics` materializes the fixed spice/vnc `<graphics>` shape; threaded into all five non-container builders (not `--container`, matching upstream's own guard) and wired into `virt-install.rs` via a `DomainCapabilities::fetch` this binary had dropped under ticket 20. **(d) built**: `domain_skeleton::push_default_clock` ports the rtc/pit/hpet timer trio (`clock.py`'s `set_defaults`), self-gating on `os_type`/`arch`/`is_qemu` exactly like upstream's own early-returns — called unconditionally from all six builders including `--container`, unlike (c), since the gate itself (not a caller-side check) excludes containers. Found and closed a real coverage gap while verifying it: every real end-to-end test in this crate runs against `test:///default`, where `is_qemu` is structurally always `false`, so none of them could reach the `is_qemu` gate against a live libvirt call — added a dedicated `VIRTINST_TEST_FAKE_URI`-based test that does. Slices (e)–(f) remain unbuilt; (f) (CPU mode defaulting, gated on building `domcaps.rs`'s `<cpu>` section) is the higher-value next pick despite being nominally last — (e) (`hostdev.set_defaults`) is still unreachable from any CLI flag. **(e) built**: `DeviceHostdev::set_defaults` (`devices/hostdev.rs`) — `managed` defaults to `!uri.is_xen()`, `mode` to `"subsystem"`, both only when unset; took `uri: &Uri` from its first draft rather than a bare `bool`, applying (c)'s correction proactively instead of waiting for a second review cycle to flag the same risk. Still no real caller (no `--hostdev` flag exists), built ahead of one anyway, same precedent as (c)'s query methods. **(f) split into two pieces on review**: the `domcaps.rs` `<cpu>` parser (real shape risk, deserves isolated verification) and the defaulting chain that consumes it — built and committed separately. **(f) piece 1 built**: `Cpu`/`CpuMode`/`CpuModel` structs plus `supports_safe_host_model`/`supports_safe_host_passthrough`/`supports_maximum_cpu_mode`, tested against a real `<cpu>` block captured from this machine's own `qemu:///session` domcapabilities (both the trimmed fixture used in unit tests and, as a one-off sanity pass, the full untrimmed 2891-line capture — confirming `find_all` on this crate's XML layer is direct-children-only, so the parser can't accidentally absorb a sibling `<feature>`/`<vendor>` element). Grounding check resolved before piece 2: unlike (b)'s q35 branch, `_get_app_default_mode`'s chain consults only these pure `domcaps.supports_*()` queries, no hv-version support-check — piece 2 is fully buildable now, not partially blocked. **(f) piece 2 built, ticket 21 fully closed**: `DomainCapabilities::default_cpu_mode` (the `_get_app_default_mode`/`set_special_mode`/`set_model`/`_validate_default_host_model_only` chain collapsed into one query returning a `DefaultCpuMode` enum) and `domain_skeleton::push_default_cpu`, following `push_default_graphics`'s "resolve once in `virt-install.rs`, pass the answer in" pattern rather than `push_default_clock`'s self-gating one — advisor caught that a `DomainCpu::set_defaults` on the bound struct (the precedent (e) set) doesn't transfer here, since `<cpu>` defaulting is unconditional in upstream, not gated behind a not-yet-existing flag the way `--hostdev` gates (e). Threaded into all four builder modules including `--container` (always `None` there, same reasoning as its `machine`/`emulator` exceptions). **A deliberate superset caught on review**: the custom-model fallback always validates the host's reported CPU model against domcaps before emitting it, but upstream only does that when `guest.x86_cpu_default == HOST_MODEL_ONLY` — pinned to `APP_DEFAULT` on `virt-install`'s own CLI path (`guest.py:273`, never reassigned there), so that validation is actually dead code for `virt-install` itself and only live via the GUI's CPU-preference setting. Kept unconditional anyway (no `x86_cpu_default`-equivalent switch exists here to gate it on, and a 1:1 GUI port is this project's stated endpoint where the behavior *is* real) — documented as a real, deliberate divergence rather than the "faithful replication" an earlier draft of the doc claimed before review caught it. Real end-to-end proof follows (d)'s pattern: a value resolved from a real captured `<cpu>` fixture survives a real `Domain::create_new`/`define_new` round trip against `test:///default` unchanged. 14 new tests (9 domcaps branch coverage, 5 shape/end-to-end), 181/181 `virtinst-core`, harness 61/61, `fmt`/`clippy` clean. All six of ticket 21's slices are now built; `--loader`/UEFI selection and the disk-bus default remain the two items confirmed fully blocked on `OsInfo`.
